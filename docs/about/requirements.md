# Функциональные требования к системе планирования доставки

## 1. Введение

### 1.1. Назначение документа

Документ определяет функциональность системы планирования доставки (далее — Система): какие задачи она решает, на основании каких данных, в каких сценариях применяется и по каким критериям принимается. Документ является основой для технического задания, плана испытаний и приёмки.

### 1.2. Область применения

Система предназначена для оперативного планирования доставки заказов со складов Заказчика с помощью курьеров внутри полигона. По текущему состоянию (известным заказам, курьерам на смене и складам) Система строит план доставки:

- объединяет заказы в поездки
- определяет порядок доставки внутри поездки
- назначает поездки курьерам
- выделяет заказы, которые не могут быть доставлены курьерами на смене и требуют привлечения дополнительных ресурсов

## 2. Общее описание

### 2.1. Предпосылки

В типовых условиях действующий механизм распределения заказов Заказчика обеспечивает приемлемые показатели. Необходимо повышение эффективности в двух областях:

- **Объединение заказов.** Как правило, один курьер доставляет один заказ за одну поездку. Объединение нескольких заказов в одну поездку позволяет снизить затраты на доставку.
- **Пиковые периоды.** В праздничные дни (например, в новогодний период) и при неблагоприятных внешних условиях (погода, загруженность дорог) за несколько минут поступают десятки заказов. Курьеров на смене не хватает, часть заказов передаётся на внутреннюю биржу курьеров или во внешние службы доставки, и расходы заметно растут.

### 2.2. Цели

1. Повысить прибыль Заказчика за счёт снижения расходов на доставку.
2. Снизить расходы в пиковые периоды, когда для доставки привлекаются внутренняя биржа курьеров и внешние службы доставки.
3. Своевременно выявлять заказы, для которых требуется привлечение дополнительных ресурсов.

### 2.3. Характеристики задачи

Задача относится к классу задач маршрутизации транспорта (Vehicle Routing Problem, VRP) и объединяет сразу пять её расширений.

| Характеристика | Содержание | Класс задач |
| --- | --- | --- |
| Неоднородный парк | Пешие курьеры, велокурьеры и автокурьеры с разной скоростью и вместимостью | HFVRP |
| Несколько складов | Заказы отгружаются с нескольких складов | MDVRP |
| Мягкие сроки доставки | Опоздание допускается со штрафом | VRPTW (soft) |
| Динамическое поступление заказов | Заказы неизвестны заранее; решения принимаются по мере их поступления | DVRP |
| Несколько поездок за смену | Курьер выполняет последовательность поездок; поездки могут начинаться с разных складов | MTVRP |

Совместный выбор группировки заказов, порядка доставки и назначения курьеров — NP-трудная задача: при реальных объёмах точное решение недостижимо за приемлемое время. Поэтому Система решает её поэтапно: сначала формирует варианты группировки заказов в поездки, затем выбирает оптимальную комбинацию поездок и их назначение курьерам.

### 2.4. Допущения

- Каждый заказ заранее закреплён за одним складом.
- Позиции курьеров на момент расчёта известны.
- Тарифы курьеров передаются в Систему вместе с исходными данными.

## 3. Архитектура системы

Оркестратор запускает контур расчёта (выделен пунктиром): данные проходят путь от хранилища через преобразование и алгоритмический модуль до плана доставки, который возвращается через интеграционный слой и отображается пользователю.

### 3.1. Назначение компонентов

| Компонент | Назначение | Требования |
| --- | --- | --- |
| Input Load Module | Загрузка исходных данных и их преобразование в формат хранилища | FR-1 |

| Domain Mapping Layer | Преобразование данных хранилища в объекты предметной области | FR-3 |
| Tariffication | Расчёт стоимости по тарифам курьеров | FR-5 |
| Algorithm Module | Проверка данных, формирование вариантов поездок, выбор оптимальной комбинации и назначение курьеров (3.2) | FR-4, FR-6…FR-13 |

### 3.2. Алгоритмический модуль

Алгоритмический модуль превращает объекты предметной области в лучшее решение за шесть шагов.

1. **Приём данных.** Интеграционный слой модуля получает заказы, курьеров, склады, тарификацию и ограничения.
2. **Проверка.** Данные проверяются и нормализуются.
3. **Кластеризация.** Формируется набор вариантов разбиения заказов на поездки (поездка = кластер).
4. **Упорядочение.** Для каждой поездки определяется порядок доставки заказов.
5. **Выбор и назначение.** Варианты вместе с остальными данными формулируются как задача оптимизации по времени и стоимости. Решение — двоичный вектор: какие поездки выбраны и каким курьерам назначены.
6. **Постобработка.** Вектор декодируется в лучшее решение и передаётся дальше для отображения.

## 5. Сценарии использования

Система работает в двух режимах — статическом и динамическом; третий сценарий описывает заказы, требующие дополнительных ресурсов, и выполняется внутри любого из них.

### UC-1. Планирование по известному набору заказов (статический режим)

| Элемент | Описание |
| --- | --- |
| Инициатор | Пользователь системы |
| Цель | Распределить известные заказы по поездкам и курьерам |
| Предусловие | Данные о заказах, курьерах на смене, складах и тарифах загружены в хранилище |
| Результат | Каждый заказ включён в поездку с назначенным курьером либо отнесён к требующим дополнительных ресурсов |

**Основной поток**

1. Пользователь запускает планирование в интерфейсе (FR-17).
2. Система запрашивает данные, преобразует их в объекты предметной области и проверяет (FR-2…FR-4).
3. Система формирует варианты поездок, выбирает оптимальную комбинацию и назначает курьеров (FR-6…FR-10).
4. Система формирует план доставки, сохраняет его и показывает пользователю (FR-14…FR-16).

**Альтернативный поток.** Данные не прошли проверку на шаге 2; поведение Системы в этом случае необходимо согласовать.

### UC-2. Непрерывное планирование (динамический режим)

| Элемент | Описание |
| --- | --- |
| Инициатор | Оркестратор Системы по расписанию |
| Цель | Обслуживать непрерывный поток новых заказов |
| Предусловие | На момент запуска часть заказов уже распределена по курьерам, часть — нет |
| Результат | Актуальный план доставки по состоянию на момент каждого запуска |

**Основной поток**

1. Оркестратор запускает расчёт (FR-19).
2. Система получает текущее состояние, включая уже распределённые заказы (FR-11).
3. Система выполняет шаги 2–4 сценария UC-1.
4. Через X минут цикл повторяется с новым состоянием.

Каждый запуск строит план по текущему состоянию, а не корректирует предыдущий план.

### UC-3. Заказы, требующие дополнительных ресурсов

| Элемент | Описание |
| --- | --- |
| Контекст | Выполняется в рамках UC-1 или UC-2 |
| Цель | Своевременно выявить заказы, которые необходимо передать на внутреннюю биржу или во внешнюю службу доставки |
| Результат | Список таких заказов в составе плана доставки |

**Основной поток**

1. При планировании Система определяет, что заказ не может быть доставлен курьерами на смене (FR-12, FR-13).
2. Заказ включается в список заказов, требующих дополнительных ресурсов.
3. Список передаётся в составе плана доставки (FR-14).

## 6. Бизнес-правила и модель стоимости

### 6.1. Бизнес-правила

Любой план доставки, сформированный Системой, должен удовлетворять следующим правилам

| ID | Правило |
| --- | --- |
| BR-1 | Используются три типа курьеров — пеший, велосипедный и автомобильный; скорость и вместимость определяются типом курьера |
| BR-2 | Каждый заказ входит ровно в одну поездку; каждая поездка выполняется ровно одним курьером |
| BR-3 | Все заказы одной поездки отгружаются с одного полигона |
| BR-4 | Суммарная масса заказов поездки не превышает вместимость назначенного курьера |
| BR-5 | Маршрут поездки начинается на складе, проходит каждый адрес поездки один раз и завершается у последнего адреса |
| BR-6 | Поездка отправляется не раньше, чем готовы все её заказы, и не раньше, чем курьер прибудет на склад после предыдущей поездки |
| BR-7 | Курьер может выполнить за смену несколько поездок, в том числе с разных складов; переезд между поездками учитывается по времени, но не тарифицируется |
| BR-8 | Доставка после срока допускается; за каждую минуту опоздания начисляется штраф |
| BR-9 | Курьеры на смене работают в пределах полигона обслуживания |

### 6.2. Модель стоимости

Система минимизирует суммарную стоимость плана: стоимость поездок, фиксированную стоимость задействованных курьеров и штрафы за опоздания. Все тарифные коэффициенты задаются по типу курьера.

Стоимость поездки j, выполненной курьером k:

$$
C_{kj} = \tau^{trip}_k + \alpha_k \cdot H(k, \Omega_j) + \beta_k \sum_{a \in \Omega_j} w_a + \gamma_k \cdot |\Omega_j|
$$

Целевая функция:

$$
\min \sum_{k \in K} \sum_{j \in J} x_{kj} C_{kj} + \sum_{k \in K} \tau^{shift}_k y_k + \sum_{a \in O} \pi \cdot \max(0,\ t^{arr}_a - d_a)
$$

| Обозначение | Смысл |
| --- | --- |
| τtrip\_k | Фиксированная стоимость поездки |
| α\_k | Стоимость километра |
| β\_k | Стоимость килограмма |
| γ\_k | Стоимость доставки одного заказа |
| τshift\_k | Фиксированная стоимость курьера, задействованного в плане |
| H(k, Ω\_j) | Длина оптимального маршрута поездки, км |
| w\_a, d\_a, t\_arr | Масса заказа, срок доставки и фактическое время прибытия |
| π | Штраф за минуту опоздания |
| x\_kj, y\_k | Курьер k выполняет поездку j; курьер k задействован (0 или 1) |

## 7. Модель данных

### 7.1. Входные сущности

После преобразования данных хранилища (FR-3) в планировании участвуют пять сущностей.

| Сущность | Структура | Атрибуты |
| --- | --- | --- |
| Заказ | `orders: List[Order]` | Координаты адреса доставки, масса, склад отгрузки, время готовности, срок доставки |
| Курьер | `couriers: List[Courier]` | Тип, скорость, вместимость, начальная позиция |
| Склад | `warehouses: List[Warehouse]` | Координаты |
| Тарификация | `tariffication: Tariffication` | Тарифные коэффициенты по типам курьеров и штраф за опоздание (раздел 6.2) |
| Ограничения | `constraints: Constraint` | Параметры ограничений планирования; состав уточняется |

### 7.2. Промежуточные данные

| Данные | Структура | Назначение |
| --- | --- | --- |
| Результат проверки | `isValidated, isNormalized` | Признаки того, что данные прошли проверку и нормализацию |
| Варианты разбиения | `Set(Set(Tuple(Courier.type, List[Order])))` | Набор вариантов; вариант — множество поездок, поездка — тип курьера и список заказов |
| Решение задачи оптимизации | Двоичный вектор | Кодирует выбранные поездки и их назначение курьерам |

### 7.3. Результат планирования

Двоичный вектор декодируется в лучшее решение (`PlanningResult`), которое содержит:

- поездки — склад, тип курьера, упорядоченный список заказов, время отправления;
- назначение поездок курьерам и последовательность поездок каждого курьера;
- заказы, требующие дополнительных ресурсов.

Результат сохраняется через интеграционный слой и передаётся в пользовательский интерфейс в виде форматированных объектов. Форматы и протоколы обмена с системами Заказчика необходимо согласовать.

## 8. Нефункциональные требования

В пиковые периоды за несколько минут поступают десятки заказов, если расчёт не успевает за потоком, заказы накапливаются необслуженными. Поэтому ключевое нефункциональное требование — время расчёта.

| ID | Категория | Требование |
| --- | --- | --- |
| NFR-1 | Производительность | Один расчёт плана выполняется за секунды — не более T с |
| NFR-2 | Масштабируемость | NFR-1 выполняется при нагрузке полигона до N заказов, K курьеров и D складов на момент расчёта |
| NFR-3 | Надёжность | Некорректные входные данные выявляются до начала планирования (FR-4) |
| NFR-4 | Расширяемость | Правила отнесения заказов к требующим дополнительных ресурсов изменяются без изменения алгоритма планирования (FR-13) |

## 9. Приёмка и оценка качества

Система принимается по итогам полевых испытаний на действующем полигоне Заказчика; до испытаний качество решений проверяется на тестовом наборе задач.

### 9.1. Этапы

| Этап | Содержание | Результат |
| --- | --- | --- |
| 1. Разработка и внутренняя проверка | Реализация требований, проверка на тестовом наборе задач | Система готова к испытаниям |
| 2. Полевые испытания | В течение нескольких месяцев доставка на выбранном полигоне планируется Системой | Данные о работе полигона |
| 3. Оценка результата | Сравнение показателей полигона до и после внедрения | Решение о приёмке |

### 9.2. Оценка качества решений

На небольших задачах план Системы сравнивается с оптимальным, найденным точным перебором. Тестовый набор покрывает разные условия: расположение заказов относительно склада, нагрузку на курьеров и число складов (от одного до трёх). Основная метрика — относительное отклонение стоимости от оптимума:

$$
gap = \frac{C_{heur} - C_{opt}}{C_{opt}}
$$

где C\_heur — стоимость плана Системы, C\_opt — стоимость оптимального плана; обе рассчитываются по модели стоимости из раздела 6.2. Дополнительно сравнивается сама группировка заказов: два плана равной стоимости могут требовать разного числа курьеров. Для этого используется скорректированный индекс Рэнда (ARI).
